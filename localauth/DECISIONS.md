# localauth · 设计决定与「为什么不做 X」

> 本文件记录**已经裁定、不再重开**的决定。每条都来自 geass-v3 宿主期（2026-09-04 ～ 09-06）的
> 实测或裁决，出处是 config 私有仓 `cross-exam/2026-09-04-localauth-delivery-checklist.md`（§ 号对应那里）。
> 要推翻任何一条，先读那一节的实测记录。

## 边界（模块永远不做的事）

| # | 不做 | 为什么 |
|---|---|---|
| 1 | **不认识用户模型**：角色、档案、业务字段、「哪一列算已验证邮箱」 | 这些每个宿主都不一样。模块只回答"这次尝试放不放行"，用户从哪来、放行后签什么、失败后给用户看什么全是宿主的事（§1.6 / §19.3） |
| 2 | **不做本地账号与联邦（OIDC）账号的绑定 / 合并 / 解绑** | 用户 2026-09-06 裁定：本地登录与 OIDC 登录是**两套并行的登录，不关联**。⛔ 不要在模块里加任何绑定入口，identities 类的表也不进契约（§33） |
| 3 | **不碰数据库、不签 token、不发邮件** | 全部经契约注入：`FailureStore` / `SessionStore` / `VerificationStore` / `CredentialStore` / `MessageSender` / `AccessTokenIssuer`。模块里出现任何一个具体应用的字符串都是抽象泄漏（`doc.go` 两条铁律） |
| 4 | **权限不进 JWT** | 权限是可变状态，进了 token 就要等 TTL 才失效；模块的会话吊销与纪元只管"这个人此刻还算不算登录"，权限由宿主每次查（§24） |
| 5 | **准入匹配只支持精确匹配与单个 `*`，不做 `cluster:*` 这类部分通配** | 匹配器是安全 bug 的产地；宿主要复杂规则就在自己的 `Admission` 实现里写（§22） |
| 6 | **不做递增延迟式退避** | 任何"响应时间随账号状态变化"的机制本身就是预言机，与时序一致直接对立。退避是**拒绝**，不是**变慢**（`policy.go`） |
| 7 | **不做锁定提示文案** | 只给类型化错误码（`errors.go` 的 `Code*`），文案是宿主的 i18n（§8.4） |

## 安全上不可动摇的（改了就是洞）

| # | 规则 | 出处 |
|---|---|---|
| 8 | bcrypt 只有一个调用点，用户不存在也跑等量工作（合法的 dummy hash），错误在原地坍缩为 bool | `doc.go` 六条；§21 记录了"dummy 代换后照常返回比对结果"这个按设计实现就会产生的绕过，已修 |
| 9 | 计数键是**用户提交的原始字符串**，对不存在的用户名同样计数；两个维度是两个独立计数器，不合成复合键 | 否则计数器自己就是枚举预言机；复合键被两个维度的轮换分别绕开 |
| 10 | **`Bump` 必须原子自增**并返回自增后的状态，⛔ 不得 Load+Save | 副本 > 1 时读-改-写竞态让计数丢失，退避形同虚设（§3.3；`storetest` 有并发断言） |
| 11 | 账号维度的计数键列必须与用户名列**共享同一条排序规则**，且在 DDL 里显式钉死 | 本地 MySQL 与 TiDB 的默认排序规则不同，"本地试过没问题"在生产上正好是最严重的那种漏。⛔ 不要在 Go 侧自己写规范化去"对齐"（`store.go`） |
| 12 | **`Rotate` 必须原子**，且必须区分 `Replayed`（命中上一个哈希）与 `Revoked`（命中当前哈希但会话已死） | 2026-09-05 之前只返回 bool 并"一律当重放"，后果是"登出其它设备"变成几秒后全员掉线（`session.go`）。`RotateUnknown` 刻意占零值位：实现忘了赋值时后果是拒绝本次，不是吊销全部 |
| 13 | 会话存储的参数只有**哈希**，明文 refresh token 在类型上写不出来 | 宿主此前 122 份活凭证明文入库（§13.3） |
| 14 | 吊销纪元判定用 `iat < epoch`，**相等不算失效** | 改密紧接着重签，新 token 与纪元落在同一秒；相等算失效 = 改完密码立刻掉线，100% 复现。封禁 / 全部登出因此用 `RevokeIssuedThrough`（推到下一秒起点）——两句话不一样，所以是两个方法（`revocation.go`，§26） |
| 15 | 吊销检查 **fail-open + 可计数的降级事件**，超时 300/200/200 ms 且不重试 | 本地实测 Redis 挂掉时默认超时让每次判定耗 1.68 s，fail-slow 比 fail-open 危险得多（`redisstore`）；"没有纪元"不发事件，否则噪声淹没真故障 |
| 16 | 泄露检查 `BreachUnknown` 占零值位（查不成 = 放行），但 `Skipped ≠ Clean`，且**警告放行**而非拒绝 | 用户裁决 2026-09-05：命中泄露也放行，把次数带到前端提示（`password_policy.go`） |
| 17 | 验证码：`(subject, purpose)` 作 selector，"根本没有"不计 attempts、"找到但不对"才计；一人一码；`Consume` 一次性原子 | 攻击者猜码只能消耗那一行的几次机会，猜不存在的邮箱什么都消耗不到（`verification.go` §23） |
| 18 | 找回口令只认**本应用验证过的地址**，请求与完成两次解析，地址变了就拒绝 | 2026-09-05 实测到的接管链：先换恢复地址再申请找回（§18.3） |
| 19 | 改邮箱：先验证新地址、写入、通知旧地址、吊销全部会话、推进纪元、重签当前设备 | 用户裁决 D3「吊销全部 + 重签当前设备」 |

## 工程纪律（测试与替身）

| # | 规则 | 为什么 |
|---|---|---|
| 20 | **fake 的精度必须与真实存储一致**：内存实现的时间截到整秒 | 内存 store 曾保留亚秒而 Redis 存整秒，`13:00:14 < 13:00:14.7` 只在 fake 里成立，掩盖的正是精度类缺陷（§26） |
| 21 | 存储实现用 `storetest` 的契约测试验，不只跑守卫的单测 | 守卫单测证明的是"如果存储语义正确，编排就正确"；存储语义本身要另验 |
| 22 | 内存实现只供单副本与测试；`NewRevocationChecker(nil)` 是合法配置但每次判定发降级事件 | 静默退化最危险：症状与"一切正常"完全一样 |
| 23 | 审计事件 `EventKind` 封闭枚举，`AllEventKinds()` 供宿主做穷举映射测试 | 宿主曾把新事件漏在日志映射外，事件发了没人看见 |

## 版本

- `v0.1.0`（2026-09-06）：从 geass-v3 `pkg/localauth` 剥离，API 面与宿主期一致，文件平铺不拆子包（验收期不改 API 面）。
  唯一结构变化：Redis 实现移到 `redisstore/`，让不用 Redis 的宿主不 import go-redis。
- v0 期间 API 可改；两家宿主（geass-v3、melete）稳定后升 v1.0.0。
